# Phase 7 — CRM et consentements : cadrage

Date : 28 octobre 2026. Précède l'implémentation (§22 du prompt maître).

## 1. Périmètre

Vue contact unifiée **par organisation** (jamais partagée entre organisations) : fiche nourrie automatiquement par les commandes, adhésions, candidatures bénévoles et missions publiées ; création et recherche manuelles ; identités (e-mails, téléphone, compte utilisateur vérifié) ; **historique de participation** (événements, commandes, billets, adhésions, bénévolat) ; tags ; notes internes ; **historique de consentement** par canal (e-mail) avec base légale, preuve et provenance ; **liste d'exclusion** (suppressions) consultable sans réinscription automatique ; **segments** dynamiques (filtres combinables évalués en SQL, recalculés à la demande) et statiques ; **fusion** de doublons avec enregistrement de fusion ; **export CSV** soumis à `contacts.export` et tracé dans l'audit ; indicateurs (contacts, consentis, exclus, nouveaux 30 j). Écrans : contacts (liste + filtres), fiche contact (360°), segments (partie « audience » de l'écran 19), exclusions ; nav « Contacts ».

Hors périmètre : campagnes, envois, lien de désinscription public, rebonds (phase 8 — ils écriront dans `contact_suppressions` et `consent_records` via les commandes de ce module) ; effacement / anonymisation RGPD complet et export de portabilité (phase 10 « opérations », le module expose déjà tout l'historique par contact) ; enrichissement externe ; dédoublonnage automatique (proposition de doublons seulement, fusion toujours humaine).

## 2. Existant réutilisé

`orders` (`buyer_email`, nom, `marketing_opt_in`, `user_id`), `tickets` / `checkins` (participation), `memberships` et `membership_applications` (`member_email`, `marketing_opt_in`), `volunteer_applications` (`email`, `marketing_opt_in`, `user_id`, téléphone, année de naissance), `active_volunteer_commitments` (missions publiées), `users` (identité vérifiée), audit, outbox, RBAC (`contacts.read`, `contacts.export`), `TableContainer` / filtres / `EmptyState` du design system.

Catalogue RBAC : nouvelle permission **`contacts.manage`** (fiches, identités, tags, notes, consentements manuels, exclusions, segments, fusions) attribuée aux rôles `owner`, `organization_admin`, `event_manager`, `marketing_manager`, `ticketing_manager`. `contacts.read` reste la lecture ; `contacts.export` l'export. Motif : le prompt maître impose deny-by-default et des permissions atomiques ; confondre lecture et écriture sur la base de contacts contredirait la minimisation.

## 4. Alimentation du CRM (règle de dépendance n° 3)

Les modules propriétaires (ticketing, memberships, volunteers, scheduling) **appellent la commande publique** `recordTouchpoint(tx, …)` du module `crm` **dans leur transaction** : commande payée, adhésion activée / renouvelée, candidature déposée / acceptée, mission publiée. La commande crée ou met à jour le contact (par e-mail normalisé, puis par identité), rattache le compte utilisateur quand l'e-mail est vérifié, met à jour les compteurs et `last_activity_at`, et écrit un `consent_record` **uniquement** si la source porte une information de consentement (`marketing_opt_in = true` → `granted / explicit_opt_in` ; sinon `granted / customer_exception` pour un achat ou une adhésion payante, jamais pour une candidature bénévole). **Une transaction, une adhésion ou une candidature ne vaut jamais consentement marketing** : `marketing_email_status = customer_only` est distinct d'`opted_in` et exclu des segments « consentis ». Une commande `rebuildContacts(orgId)` idempotente rejoue tout l'historique (reprise des données des phases 3–6, bouton « Reconstruire depuis l'historique » réel) ; le worker la planifie chaque nuit comme filet de sûreté.

## 5. Segments (définition jsonb validée par Zod, évaluée en SQL)

Groupes de règles combinés en ET ; chaque règle : `tag` (in / not in), `marketingEmail` (statuts), `event` (a participé / a commandé / a été bénévole à l'un des événements), `membership` (adhésion active / expirée / jamais ; formule), `volunteer` (candidature acceptée / mission publiée), `orders` (nombre ≥, montant ≥), `activity` (dernière activité avant / après), `source`, `search`. L'évaluation renvoie le nombre et la liste ; le résultat n'est **pas** figé pour un segment dynamique (recalcul à l'affichage, et à l'envoi en phase 8) ; un segment statique conserve ses membres.

## 6. API et UI

Routes `/api/v1/organizations/{id}/…` : `contacts` (GET filtres + recherche, POST), `contacts/duplicates` (GET : candidats doublons par nom / téléphone), `contacts/export` (GET CSV, `contacts.export`, audité), `contacts/{contactId}` (GET 360°, PATCH), `contacts/{contactId}/{archive|restore}`, `contacts/{contactId}/notes` (POST) + `…/notes/{noteId}` (DELETE), `contacts/{contactId}/tags` (PUT liste), `contacts/{contactId}/consents` (POST manuel : granted / withdrawn avec preuve obligatoire), `contacts/{contactId}/merge` (POST `{ mergedContactId, reason }`), `contact-tags` (GET/POST/PATCH/DELETE), `suppressions` (GET, POST, `…/{id}/lift`), `segments` (GET/POST), `segments/{segmentId}` (GET avec aperçu, PATCH, DELETE), `segments/{segmentId}/evaluate` (POST → nombre + échantillon), `segments/preview` (POST définition → nombre), `crm/rebuild` (POST). UI : `/o/[slug]/contacts` (indicateurs, recherche, filtres : consentement, tag, source, événement ; export ; doublons), `/o/[slug]/contacts/[contactId]` (identités, consentement avec journal, tags, notes, historique chronologique commandes / billets / adhésions / bénévolat / missions, fusion), `/o/[slug]/contacts/segments` (+ `nouveau`, `[segmentId]` : constructeur de règles, aperçu en direct), `/o/[slug]/contacts/exclusions`.

## 7. Sécurité

Isolation stricte : toutes les tables portent `organization_id` et des FK composites ; une identité (`user_id`, e-mail) commune à deux organisations donne **deux contacts indépendants** ; aucune route ne liste ni ne recherche hors de l'organisation (autre organisation : 404). Lecture `contacts.read`, écriture `contacts.manage`, export `contacts.export` (audité : filtre, nombre de lignes, acteur). Notes internes absentes de toute réponse publique (aucune route publique dans cette phase). Consentements append-only : un retrait n'efface pas l'historique ; une exclusion n'est levée que par action explicite motivée (jamais par une nouvelle commande ou un nouvel opt-in automatique). Fusion : réservée à `contacts.manage`, deux contacts de la même organisation (sinon 404), instantané conservé, irréversible et documentée comme telle.

## 8. Tests attendus

Unitaires : normalisation des identités, calcul de `marketing_email_status` à partir du journal, compilation des règles de segment. Intégration : alimentation par commande payée / adhésion / candidature / mission publiée (statuts `customer_only` vs `opted_in`), reconstruction idempotente, isolation (même e-mail dans deux organisations = deux contacts, autre organisation 404), recherche et filtres, tags et notes, consentement manuel avec preuve obligatoire, retrait, exclusion puis levée motivée, fusion (identités, tags, notes, consentements, historique rattachés ; fusionné en `merged`), segments dynamiques (consentis seulement ; événement ; adhésion active) et statiques, export CSV audité, permissions (lecture sans écriture 403, export sans `contacts.export` 403). Sécurité S9 par API directe : outsider, autre organisation, lecteur sans `contacts.manage`, export sans droit. E2E : commande + adhésion + candidature → contacts automatiques avec statuts de consentement distincts → fiche 360° → tag + note → segment « consentis ayant participé » (comptage réel) → exclusion → fusion de doublons → export.

## 9. Hypothèses (décidées)

- Alimentation **synchrone** dans la transaction source (règle n° 3) plutôt que par consommateur d'outbox : cohérence immédiate pour l'organisateur, aucune file nouvelle ; la reconstruction nocturne couvre les cas de reprise.
- Clé de rapprochement = e-mail normalisé (minuscules, espaces retirés) ; téléphone normalisé E.164 (France / Suisse par défaut) uniquement pour la détection de doublons ; jamais de rapprochement automatique par nom seul.
- `customer_exception` (exception « client existant », art. L.34-5 CPCE) est **enregistré** comme base légale mais **exclu par défaut** des segments ; la phase 8 décidera, campagne par campagne, si une organisation l'invoque pour des offres analogues — avec le lien de désinscription systématique.
- Un contact archivé reste dans l'historique (commandes, missions) mais sort des listes et segments par défaut ; il est restaurable.
- L'export CSV est en UTF-8 avec BOM, séparateur `;` (Excel francophone), sans notes internes.
