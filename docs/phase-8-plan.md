## 1. Périmètre

Écrans : 19 (campagnes), 20 (éditeur), 21 (vérification) ; rapport ; page publique de désinscription ; nav « Marketing ».

Hors périmètre : éditeur visuel par blocs (Markdown restreint livré), A/B testing, suivi d'ouverture par pixel (volontairement absent : peu fiable et intrusif ; le guide UX précise que « envois » et « clics » n'impliquent pas de suivi d'ouverture), SMS, `notification_preferences` / `notifications` internes (phase 9 — opérations et tâches), import de contacts.

## 4. Machine à états de la campagne

`draft → scheduled` (vérification validée, audience instantanée) · `scheduled → draft` (déprogrammer) · `scheduled → cancelled` (avant le début) · `scheduled → sending` (worker, verrou `FOR UPDATE SKIP LOCKED`) · `sending → sent` (tous envoyés) · `sending → partially_failed` (certains échecs définitifs) · `sending → failed` (aucun envoi) · `draft → cancelled`. `sent` / `partially_failed` / `failed` / `cancelled` terminaux ; **une campagne lancée n'est jamais annulable rétroactivement** (le guide UX). Toute transition est auditée.

## 5. Envoi (worker)

1. Prendre une campagne `scheduled` échue (verrou) → `sending`, `started_at`.
2. Résoudre l'audience **maintenant** (`resolveDefinition` du segment), puis par contact : exclure `status <> active`, adresse invalide, `marketing_email_status` ∉ {`opted_in`} (∪ {`customer_only`} si `include_customer_exception`), adresse exclue (`contact_suppressions` actives), doublon d'adresse ; écrire l'instantané `campaign_audiences` et les `campaign_recipients` (`pending` ou `skipped` + motif). Idempotent : un destinataire déjà `sent` n'est jamais recréé ni renvoyé.
3. Envoyer les `pending` par lots (`CAMPAIGN_BATCH_SIZE`, défaut 50) : rendu personnalisé (liens suivis, jeton de désinscription dérivé par destinataire), `message_deliveries` `queued` → `accepted` ; échec → `attempts + 1`, nouvel essai au lot suivant jusqu'à 3, puis `failed`. Chaque lot est une transaction courte ; un redémarrage reprend sur les `pending`.
4. Clôture : compteurs, `finished_at`, statut final, audit, outbox `campaign.finished`.

## 7. Sécurité

Envoi réservé à `campaigns.send` (distinct de `campaigns.manage`) ; isolation par FK composites (segment, gabarit, campagne d'une autre organisation : 404) ; éligibilité revalidée **à l'envoi**, jamais depuis l'instantané seul ; aucune adresse exclue ni non consentie ne reçoit un message (test d'intégration par assertion sur la boîte de sortie) ; jetons de désinscription et de destinataire dérivés HMAC, jamais stockés, 404 uniforme ; rappels fournisseur signés (HMAC, rejeu idempotent par `provider_message_id`) ; pas d'IP dans les événements de suivi ; attribution seulement par jeton valide (aucune résolution d'identité par e-mail) ; redirection de lien suivi uniquement vers la cible enregistrée (jamais d'URL ouverte) ; contenu HTML échappé (Markdown restreint, pas de HTML brut).

## 8. Tests attendus

Unitaires : rendu Markdown restreint (échappement, boutons, liens suivis), personnalisation, construction d'URL d'attribution, machine à états. Intégration : brouillon → test → vérification (compte, motifs d'exclusion) → programmation (instantané) → **contact désinscrit après la programmation absent de l'envoi** → envoi par lots (boîte de sortie : seulement les éligibles, un message par adresse malgré deux contacts fusionnés / doublons) → reprise après panne simulée sans doublon → échec fournisseur puis succès (tentatives) → rappel de rebond → exclusion + destinataire `bounced` → clic suivi → commande attribuée (payée) → rapport ; annulation après lancement refusée ; autre organisation 404 ; `campaigns.manage` sans `campaigns.send` → 403 à la programmation. Sécurité S10 par API directe. E2E : campagne créée → test envoyé → vérification → envoi immédiat → worker (lancé par le script de test) → rapport « envoyée » → lien de désinscription depuis l'e-mail reçu → exclusion visible.

## 9. Hypothèses (décidées)

- **Pas de suivi d'ouverture** (pixel) : métriques = envois, livraisons, rebonds, clics, désinscriptions, commandes attribuées.
- Markdown restreint (titres, paragraphes, gras, liens, listes, bouton `> [Texte](url)`) rendu en table HTML responsive ; aucun HTML brut accepté.
- L'« exception client » n'est incluse que par décision explicite à la vérification, avec note tracée dans l'audit et dans la campagne.
- `CAMPAIGN_BATCH_SIZE` (défaut 50) et `EMAIL_WEBHOOK_SECRET` (signature des rappels du fournisseur simulé et de Resend) ajoutés à l'environnement.
- Les e-mails de test passent par le port e-mail avec `kind = test` dans `message_deliveries` et ne touchent jamais le statut d'un destinataire.
